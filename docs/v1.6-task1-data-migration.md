# GYM OS V1.6 — Task 1: Training data foundation and migration contract

Status: design baseline only; implementation and verification pending. Do not merge until owner approves.

## Current-state inventory (main)
- Personal data: IndexedDB `gym-os-personal`, version 1, object store `snapshot`, key `data`.
- Stored shape: `DemoData`, validated by `isDemoData` / `isPersonalData`.
- Backups: `{ schemaVersion: 1, exportedAt, data }`; restore validates before replacing the snapshot.
- Demo: separate localStorage key `gym-os-v1.2-demo`.
- Personal repository serializes commits/restore/export and blocks operations after failed writes.
- Existing homeSessions are confirmed, user-entered sessions; Smart Plan B must remain unchanged.

## Task 1 data contract (proposed)
Define separately typed:
- `TrainingPreferences`: place ('gym' | 'home' | 'both'), daysPerWeek (3 | 4 | 5), level (existing beginner/intermediate/advanced), restrictions referencing current knee/shoulder preferences; distinguish unset preferences from defaults.
- `ExerciseDefinition`: stable exercise ID, Arabic name, location/equipment, primary muscles, ordered safety/technique instructions, contraindication tags, substitutions. This is a versioned static catalog, NOT duplicated inside each user snapshot.
- `TrainingPlan`: ID, catalog version, selected schedule template, days and exercise IDs, creation timestamp; preserve historical plans.
- `TrainingSession`: ID, plan/day reference, ISO date, state ('in_progress' | 'completed' | 'abandoned'), start/end timestamps, performed exercise IDs, actual sets/reps/load (nonnegative finite values), skipped entries, confirmed minutes; one source-of-truth for completion.
- `TrainingData`: preferences, plans, sessions; initially empty and backward compatible.

## Migration / persistence invariants
1. Existing IndexedDB data and version-1 backup must load unchanged. Introduce an explicit, pure, idempotent `upgradePersonalData` that adds only empty training data when missing; preserve meals, favorites, water, activities, weights, homeSessions, settings, declinedDate and record IDs exactly.
2. Validation must distinguish *legacy* snapshots from *current* snapshots. Invalid/corrupt records must be rejected rather than silently replaced with empty data. A failed read or migration must not overwrite storage.
3. Make one atomic snapshot write per migration, after successful validation. Retain the repository's serialized operations and blocked-write behavior. Do not delete/recreate IndexedDB or clear localStorage.
4. Introduce backup schemaVersion 2 for exports containing training data. Continue accepting schemaVersion 1 imports via the same pure upgrader. Reject unknown versions and malformed records before restore. Restoring v1 should result in empty training data without dropping existing legacy fields.
5. Ensure `DemoData` fixtures and demo persistence accept upgraded data while keeping demo/personal isolation. Never import demo data into personal storage implicitly.
6. Maintain exact existing semantics of Smart Plan B and weekly activity; training session minutes must not be counted in activity twice. Task 1 must not yet alter dashboard totals or create workout UI.
7. No network/server/API requirement. No PWA cache wipe, no forced reinstall, no user data reset.

## Acceptance tests required before PR is ready
- Legacy personal snapshot migration: exact preservation of every preexisting field, plus empty training data; repeat migration yields identical result.
- Legacy v1 backup restore, v2 backup export/restore, invalid version, invalid nested training data and duplicate IDs.
- Failed migration/write leaves durable previous snapshot unchanged and keeps recovery safeguards.
- Concurrent commit/export/restore remains serialized; exports contain committed data only.
- Demo isolation and fresh personal initialization.
- No double-counted minutes with existing homeSessions and activities.
- Existing typecheck, unit tests, build, Playwright smoke all pass.

## Out of scope for Task 1
Exercise content, 3–5 day plan generation, workout screens, set logging UI, progress charts, remote AI, design changes. These belong to Tasks 2–5.

## Implementation order
1. Add typed training domain model and pure upgrade/validation functions.
2. Wire the upgrader into personal read/restore and backup v1/v2 handling without weakening validation.
3. Add exhaustive regression tests for migration and preservation.
4. Run CI; resolve failures within Task 1 scope.
5. Owner reviews PR and explicitly approves merge. No deployment or merge beforehand.
